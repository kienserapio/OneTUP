# OneTUP sync worker

Reads a student's schedule from ERS, once, and returns it parsed. That is the
entire job.

It exists as a separate deployable for three reasons: it needs a real browser
runtime, which Vercel functions and Supabase Edge cannot provide; it has a
different scaling and failure profile from the rest of the system; and it is the
only component that ever touches an ERS credential.

## The constraints

These are not conventions. They are the reason the architecture is shaped this
way, and a change that breaks one of them is a change to the product's security
posture, not a refactor.

- **No database access.** The worker holds no Supabase URL, key or connection
  string. Compromising it yields nothing at rest.
- **No persistence.** Nothing is written to disk. The only writable path in the
  container is Chromium's temporary profile directory.
- **No credential ever reaches a log.** Request bodies are never logged, in
  success or in failure. No log line carries a field that could hold one.
- **Fresh browser context per scrape**, destroyed unconditionally in a `finally`.
- **Hard 60-second timeout per job**, enforced in `server.ts`, not left to
  Playwright.
- **Shared-secret auth**, compared without early exit, rotated quarterly.
- **Global concurrency cap.** A burst of simultaneous logins from one source is
  exactly the traffic shape that looks like an attack to whoever monitors ERS.
  Staying quiet is part of being a good citizen on infrastructure we do not own.

## Running it

```sh
pnpm install
pnpm --filter @onetup/worker dev
```

Environment (see `.env`, generated by `pnpm env` at the repo root):

| Variable | Purpose |
| --- | --- |
| `PORT` | Listen port, default 8787 |
| `WORKER_SECRET` | Shared secret the app authenticates with. Required — the worker refuses to start without it |
| `ERS_BASE_URL` | Portal base, default `https://ers.tup.edu.ph/aims/students/` |
| `WORKER_MAX_CONCURRENCY` | Simultaneous scrapes, default 10 |
| `WORKER_JOB_TIMEOUT_MS` | Per-job ceiling, default 60000 |

## Interface

```
POST /scrape/schedule
Authorization: Bearer <WORKER_SECRET>

{ "student_number": "...", "password": "...", "birthdate": "YYYY-MM-DD" }
```

Returns the parsed schedule, or a structured error. The request body is never
echoed, in success or in failure.

| Condition | Code | HTTP |
| --- | --- | --- |
| Still on the login URL after submit | `ERS_AUTH_FAILED` | 401 |
| Portal unreachable | `ERS_UNAVAILABLE` | 503 |
| Logged in, no schedule table | `SCHEDULE_NOT_FOUND` | 404 |
| Table present, nothing parsed | `SCHEDULE_PARSE_FAILED` | 422 |
| Job exceeded the timeout | `ERS_TIMEOUT` | 504 |

The authentication failure message deliberately does not say which of the three
fields was wrong. Saying so would make this endpoint useful for probing.

## The fragile part

Step 5 of the login (`setBirthdate` in `scrape.ts`). The portal's birthdate
field is `readonly` and driven by a datepicker widget, so assigning `value` is
not enough — the widget's own handlers never run and the form rejects with the
same message it gives for a wrong password. The fix is to remove the attribute,
assign, then dispatch `input`, `change` and `blur`.

If imports start failing across the board, check this and the column indices in
`SCRAPER_CONFIG` first. Both are versioned so a portal change is a config edit
and a version bump rather than a redeploy of parsing logic — and the version is
recorded on every import, so a regression can be traced to the parser that
produced it.

## Deploying

```sh
docker build -f apps/worker/Dockerfile -t onetup-worker .
docker run -p 8787:8787 -e WORKER_SECRET=... onetup-worker
```

Any container host works. It needs no volume, no database, and no inbound access
beyond the application origin.

## Testing against the real portal

A mock is not enough — the value of this service is in handling the real thing's
quirks. Test with the maintainer's own account and explicitly consenting pilot
volunteers only. Recorded HTML fixtures with every personal value replaced live
in the parser's unit tests, which is where the column and day-code handling is
actually verified.
